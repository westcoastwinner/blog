## 论文进展情况

**论文题目：**《基于微服务的数据交易系统的设计与实现》

### 一、选题背景

随着《数据二十条》的颁布和数据要素市场化配置改革持续推进，数据资源的流通利用、合规交易与价值释放已成为数字经济发展的重要方向。近年来，国家层面持续推动数据基础制度建设、数据流通交易规则完善以及可信数据空间等新型基础设施建设，强调通过统一规则、可信技术和场景牵引促进数据安全高效流通。2025年，国家数据局进一步组织开展可信数据空间创新发展试点，并发布相关技术架构、标准化研究成果和典型案例，表明我国数据流通利用正由制度探索逐步走向工程化落地与规模化应用。在此背景下，建设一个面向数据产品展示、选购、下单、支付、上架管理等完整业务链路的数据交易系统，具有较强的工程实践意义。

### 二、课题内容

本论文围绕企业实际数据交易平台建设需求，设计并实现一个基于微服务架构的数据交易系统。论文研究内容主要包括以下几个方面：

1. **系统总体架构设计**
    基于微服务思想，对系统进行服务拆分与职责划分，构建包含网关、数据产品门户、购物车（选数车）、订单、支付等核心模块的系统架构，明确服务边界、调用关系及部署方式。
2. **统一接入与网关设计**
    研究网关在统一路由转发、权限校验、请求过滤及服务治理中的作用，完成网关层的设计方案，为后续多业务模块统一接入提供支撑。
3. **数据产品门户与上下架设计**
    面向数据产品展示和生命周期管理需求，设计数据产品门户模块以及数据产品登记、审核、上架、下架等流程，支撑数据产品的统一展示与运营管理。
4. **购物车（选数车）设计**
    面向数据交易场景中“先选购、后下单”的业务特点，设计购物车模块，实现数据产品暂存、条目管理、价格衔接及与订单流程的联动。
5. **支付模块设计与实现**
    针对交易系统中支付协同需求，研究支付服务在支付下单、支付结果回调、状态更新、退款协同等方面的实现机制，保障交易链路闭环。

### 三、解决方案

论文总体采用**基于 Spring Cloud 体系的微服务架构方案**。在设计思路上，以“高内聚、低耦合、服务自治、统一治理”为原则，将不同业务职责拆分为相对独立的服务模块，并通过网关进行统一接入和外部请求治理。

在具体实现上，本系统被具体拆分为网关、业务、支付、订单、选数车等多个独立的微服务。

- **网关层**负责统一入口、路由转发、基础鉴权与请求过滤，提升系统安全性和可维护性；
- **数据产品门户模块**负责数据产品信息展示、查询与前台访问支撑；
- **数据产品上下架模块**负责数据产品从登记、审核到上架发布的业务闭环；
- **购物车模块**负责承接用户对数据产品的暂存、修改与统一下单操作；
- **支付模块**负责与订单侧联动，完成支付创建、支付结果处理和交易状态同步。

该方案能够较好适应数据交易系统业务种类多、链路长、扩展频繁的特点，避免将展示逻辑、交易逻辑、支付逻辑等高度耦合在单体系统中，从而提高系统的可扩展性、可维护性与工程落地能力。

### 四、技术难点

目前论文已梳理并重点聚焦以下几个技术难点：

**网关统一治理与安全控制问题**

与传统单体应用相比，微服务架构下网关模块的设计与实现具有更高的复杂性。在单体应用中，系统通常以一个统一部署的后端程序对外提供服务，前端请求直接进入应用内部，由应用自身完成控制器分发、身份认证、权限校验和业务处理。也就是说，请求的接入、认证和业务执行大多发生在同一个进程内，系统边界清晰，调用链路相对简单，因此安全控制和访问治理通常以内嵌方式集成在应用内部即可。

但在微服务架构下，系统被拆分为多个独立服务，如支付、订单、身份认证、基础业务等模块分别由不同服务承载。此时，若仍然让前端直接访问各个微服务，会带来多个问题：一是服务地址直接暴露，系统边界不清晰；二是每个服务都要重复实现认证鉴权逻辑，导致开发和维护成本上升；三是接口安全策略难以统一，容易出现某些服务校验严格、某些服务校验薄弱的不一致现象；四是随着服务数量增加，前端调用关系也会越来越复杂，不利于系统治理与后续扩展。因此，在微服务架构中，需要通过网关作为统一入口，对外承接所有请求，再根据规则转发到对应下游服务。



以身份鉴权这一职责为例，在传统单体应用中，通常由一个统一的控制器来承担注册、登录及状态验证等逻辑。由于系统的业务功能集中部署于同一个应用进程中，用户完成登录后，应用可直接基于 Session、Cookie 或统一的本地安全上下文维护用户身份信息，后续各业务模块在同一运行环境内即可共享认证结果。因此，传统单体应用中的身份认证与权限控制往往以内聚方式嵌入应用内部实现，系统边界相对清晰，身份管理链路也较短。

而在微服务应用中，系统被拆分为多个相互独立部署和运行的服务模块，不同服务分别承担产品展示、购物车、订单、支付等不同职责。此时，如果仍由各个服务分别实现注册、登录和用户身份校验逻辑，一方面会导致认证逻辑重复建设，增加开发与维护成本；另一方面，不同服务对认证规则、权限判断标准及安全策略的实现可能存在差异，容易形成安全治理不一致的问题。此外，在服务数量不断增加的情况下，用户体系、角色体系、令牌签发、权限模型等内容若分散在各个微服务中，也会显著提高系统耦合度和后续扩展难度。

因此，微服务架构通常需要依赖独立的 IAM（Identity and Access Management，身份与访问管理）体系来统一承担认证与授权相关职责。IAM 作为独立的身份中心，负责用户登录认证、凭证校验、令牌签发、身份信息管理以及权限模型维护等工作，从而将“谁是用户、用户是否已登录、用户具备什么权限”等问题从具体业务服务中剥离出来。这样做的核心价值在于：一是实现身份能力集中化，避免各微服务重复实现认证逻辑；二是建立统一的安全标准，保证不同服务在认证与授权机制上保持一致；三是使业务服务能够聚焦自身业务处理，而不必深度耦合用户登录过程和身份管理细节。

在此基础上，网关则承担起微服务系统统一入口处的身份校验职责。用户在前端完成登录后，由 IAM 签发 Token，后续请求首先到达网关，网关需要对请求中携带的 Token 进行合法性验证，包括验证签名是否正确、令牌是否过期、签发方是否可信，以及必要时校验其中携带的用户标识、角色或租户等声明信息。只有在 Token 验证通过后，请求才被允许继续转发到下游微服务。这样，网关就将传统单体应用中分散于内部模块的认证校验能力，提升为面向整个系统边界的统一安全控制能力。

此外，网关完成 Token 校验后，还需要承担安全上下文透传的职责。由于下游微服务通常不直接参与用户登录过程，也不应重复解析和验证前端传来的全部认证信息，因此网关会在校验通过后，将可信的用户上下文信息以约定方式传递给下游服务，例如用户 ID、用户名、角色标识、租户信息等。下游服务基于这些由网关注入的上下文数据，即可完成更细粒度的业务鉴权和资源访问控制。这样不仅减少了各服务重复认证的开销，也建立了“前端请求不可信、网关校验结果可信”的安全边界。

需要指出的是，网关对 Token 的统一验证与上下文透传，并不意味着下游服务完全不再关心权限问题。更准确地说，IAM 负责解决“身份认证”和“统一授权模型”问题，网关负责解决“系统入口处的统一校验与身份传递”问题，而具体业务服务仍需结合自身资源属性执行更细粒度的业务权限判断。例如，网关可以判断请求者是否已登录、是否具备基础访问资格，但具体某个用户是否有权查看某个订单、修改某个数据产品，仍需要由相应业务服务结合资源归属关系进一步判断。由此可见，在微服务架构中，IAM、网关与业务服务共同构成了分层协作的身份鉴权体系。

因此，相较于传统单体应用将身份认证逻辑内嵌于应用内部的实现方式，微服务应用更需要借助 IAM 统一管理身份认证能力，并依赖网关在系统入口处完成 Token 验证、请求过滤和安全上下文透传，从而在多服务协同场景下实现认证能力的集中化、访问控制的一致化以及系统安全边界的清晰化。

**支付流程中的安全性和状态一致性问题**
支付业务具有异步回调、外部依赖强、失败场景复杂等特点。如何确保支付请求安全可信、如何确保支付服务与订单状态保持一致，以及如何处理重复回调、超时、异常补偿等情况，是系统设计中的重点与难点。支付模块并不是简单地“调一个第三方接口收钱”，其真正的工程难点在于：支付结果的确认是异步的，而订单状态更新、支付流水记录、后续交付触发等业务动作必须保持一致。这使支付服务成为整个交易链路中对一致性要求最高的模块之一。

在实际业务中，用户提交订单后，系统会先生成业务订单和支付单，再调用第三方支付平台发起支付。此时用户侧看到的是“支付中”状态，但系统并不能仅凭前端跳转或用户主观反馈判定支付是否成功，而必须以支付平台回调通知结果作为最终依据。难点就在于，支付平台回调具有异步性、不确定性和重复性：一方面，回调可能因为网络抖动出现延迟；另一方面，支付平台通常会进行多次重试通知，如果系统没有做好幂等控制，就可能导致同一笔支付被重复更新、重复记账，甚至重复触发订单交付。除此之外，由前端系统传递的支付请求参数和由支付平台回调时传递的请求参数都存在伪造的可能性，所以在整个过程中需要严格按照支付平台的验签规则，通过非对称加密的方式进行验签，确保资金结算正确可靠。

**数据产品上下架过程中的异步处理与并发控制问题**
 数据产品从登记到正式上架通常涉及审核、状态变更、异步轮询或多服务协同。在多实例部署场景下，需要防止重复执行、状态错乱等问题，因此涉及分布式锁、状态流转控制等工程实现难点。
